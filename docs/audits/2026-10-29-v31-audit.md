## Findings

Severity is my judgement of user impact. Every finding lists the evidence that produced it; the
ones marked FIXED were fixed in this pass with a test that fails on the old code.

### E-1 (P1) Every `name.setRecord` confirmation failed — `READ` + `PROBE` + FIXED

`domainRecordRecheck` read `record.binding.accountAddress`. The prepared record has no `binding`
field — `review/store.js` writes `accountAddress` at the top level — so the expression threw a
`TypeError` on every confirm. The surrounding `catch` re-labelled it "domain could not be read
before signing", so the user saw `REVIEW_UNAVAILABLE` on a perfectly readable domain and could never
sign the write the review had just described.

Probe evidence (stubbed `accounts.get` returning a valid domain account, record shaped exactly as
the store writes it):

```
[recheck] THREW REVIEW_UNAVAILABLE "Failed to verify domain ownership:
          Cannot read properties of undefined (reading 'accountAddress')"
```

Fix: the recheck reads `record.accountAddress`, and the four outcomes are now distinct —
readable+owned → passes; RPC failure → `REVIEW_UNAVAILABLE` with `retryable: true`; genuinely
absent → `NAME_TAKEN`; changed owner → `NOT_NAME_OWNER`; unparseable bytes → `REVIEW_UNAVAILABLE`.
`test-name-records.mjs` `[5]` asserts all five, plus that the recheck itself never signs.

> A `catch` that converts every exception into one friendly message hides the difference between
> "the chain said no" and "my own code is broken". The probe caught this only because it printed the
> `TypeError` instead of accepting the envelope.

### E-2 (P1) A live signing method was declared `auth:'unlocked'` — `READ` + FIXED

`name.setRecord` builds, signs and broadcasts a transaction. Its manifest entry said
`auth: 'unlocked'`, which means `checkAuth` never demanded the password a user has opted into for
signing (`requirePasswordForSigning`), and because the method was missing from
`TRANSACTION_METHODS` in `api-router.js` the single-flight signing guard never engaged either. This
is the v5/v22/v23 rule — *a method that signs is `auth:'signing'` and is registered as a signing
operation* — applied to the third name write.

Fix: `auth: 'signing'`, params list the fields the handler actually reads
(`expectedNetworkId`, `expectedAccountAddress`, `password`), and the method joined
`TRANSACTION_METHODS`. `test-name-records.mjs` `[6]` enables the opt-in re-auth, calls the method
through the real router without a password, and asserts `AUTH_REQUIRED` **and** that
`buildAndSign` was never reached; the same call with the password signs exactly once (control).

### E-3 (P1) An RPC outage rendered as "you do not own this domain" — `READ` + `PROBE` + FIXED

`domainRecordFacts` collapsed every failure into two booleans: a failed `getAccountInfo` produced
`domainExists: false, isOwner: false`, and the decoder turned that pair into two blocking, *false*
statements — "Domain does not exist" and "You do not own this domain". An account that exists but
does not parse produced `isOwner: false` for the same reason: a decode failure was reported as
proof of a foreign owner.

Fix: both fields are three-state (`null` = unknown, never used as `false`), and the decoder has
separate blocking warnings — `domain-unverified` / `owner-unverified` — that say the wallet could
not prove the claim rather than asserting its opposite. Probe output now distinguishes all four
cases; `[4]` pins them and asserts that an outage never produces `domain-absent`.

### E-4 (P1) The advanced-details account row was swapped and lost its annotations — `READ` + `PROBE` + FIXED

`accountRole(role, address)` takes two arguments; the decoder called
`accountRole(facts.domainAddress, 'Domain account', { writable, verified, note })`. The rendered row
was `{"role":"ta3vGKMR…","address":"Domain account"}` — an address in the label column and a prose
string in the address column — and the third argument was discarded silently because the function
ignores it.

Fix: `accountRole('Domain account (written)', facts.domainAddress)`. `[4]` asserts role and address
individually, so a future swap fails the suite instead of shipping.

> The runner-up defect shape in this repo is "tri-state tested by truthiness"; the winner is "a
> positional API called with the arguments in a plausible order". Both are invisible to
> `node --check` and to any test that only asserts the row exists.

### E-5 (P2) Thirteen error codes existed only as strings inside services — `READ` + FIXED

`coded('X')` in `name-service.js` produced 14 codes; 13 of them were absent from `ERROR_CODES`. With
a signing path now reaching them, a UI could branch only on prose. Fix: the codes the two name
services and the review kinds can emit are declared in `manifest.js` (`DOMAIN_UNREADABLE`,
`NAME_NOT_FOUND`, `NAME_TAKEN`, `NOT_NAME_OWNER`, `REVIEW_ACCOUNT_CHANGED`,
`REVIEW_NETWORK_CHANGED`, `TX_RESULT_MISSING`, the registry's `DOMAIN_CONTEXT_CHANGED` /
`DOMAIN_IS_PRIMARY` / `NAME_UNREADABLE` / `STORAGE_INVALID` / `STORAGE_VERSION`, and
`INVALID_PARAMS` / `NAME_ROOT_UNKNOWN` / `NAME_PARENT_AUTHORITY` / `PARENT_UNKNOWN` /
`RECORD_UPDATE_FAILED` / `REGISTRATION_FAILED`). `test-contract.mjs` now scrapes both services for
`coded('…')`/`err.code = '…'` and fails if any code is undeclared; `test-name-records.mjs` `[7]`
does the same for the write path. `CONTRACT_VERSION` stays 31 — this is a documentation append to
an existing version, matching how v29 appended codes.

Declaration is not enforcement: the router still propagates whatever a service throws. What changed
is that the surface is enumerable, which is what an audit can check.

### E-6 (P2) `name.reverseLookup` was `auth:'none'` and invented a `.thru` suffix — `READ` + FIXED

Three problems in one new read:

1. `auth: 'none'` made a read of **wallet-local** records reachable while the wallet is locked, and
   outside the "every name.* read is unlocked" convention. Changed to `auth: 'unlocked'`.
2. A caller-supplied `networkId` was used to select the registry to read. Every other name read is
   bound to the active network; a cross-network read here would answer a question the screen never
   asked, from records the user cannot see. A non-active `networkId` now returns
   `NETWORK_MISMATCH` instead.
3. Unqualified candidates were labelled `${name}.thru` unconditionally, so a record tracked under
   the `.id` root was reported to the Send screen as `<name>.thru` — a wrong name on the one line a
   user reads before sending. The suffix now comes from the record's own root (`tld` in the
   response); an unnameable root yields the bare label and `tld: null`. `[4]` in
   `test-name-reverse.mjs` pins the `.id` case.

The response also returned a free-text exception message in `reason`; it now returns the declared
`LOOKUP_FAILED` with the message in `detail`.

What this read is, and now says it is: candidates come from this wallet's tracked-domain registry,
not a chain-wide reverse index (the chain cannot enumerate names by owner — `docs/BACKEND_GAPS.md`).
`NO_CANDIDATE` means "this wallet knows of no name for that address".

### E-7 (P2) The review described an append as a replace — `READ` + FIXED

Opcode 2 is `APPEND_RECORD`. Setting a key that already exists does not replace the stored value:
the new pair is appended, and readers that take the first match (`find()` in both `reverseLookup`
and `domainRecordFacts`) keep showing the old one. The card said "Set domain record", and when the
key already held a *different* value it said nothing at all.

Fix: the operation is **Add domain record** / "Append a `<key>` record to `<domain>`"; a key that
already holds another value raises a non-blocking `record-appends` warning that names the existing
value and says the old one stays; the existing "already set" case keeps its informational warning
and now also says "appends". The facts bag gained `existingValue` so the decoder can say this
without inventing it.

### E-8 (P3) Documentation still described `setRecord` as gated — `READ` + FIXED

`BUILD_SPEC.md`, `DECISIONS.md`, `STATUS_AND_ROADMAP.md`, `flags.js`, `api-router.js`,
`manifest.js` and the `name-service.js` header all said the record write was gated behind
`FLAGS.NAME_SERVICE`. It is not; only `initRoot` is. All updated, and `PROJECT_LEDGER.md` gained a
v31 row.

## Reported, not fixed

### R-1 (scope) No UI reaches domain records

`grep -rn "domain-record\|setRecord" src/ui` returns nothing. The kind is reachable only through
`tx.prepareReview` with `kind: 'domain-record'`, i.e. by a caller outside the shipped UI. Everything
above makes that path correct for whoever wires the screen; it is not a user-visible feature today,
and no doc should say otherwise. `test-name-records.mjs` drives it through the real router, which is
the closest thing to a caller that exists.

### R-2 (P3, from v30) The custom registrar's fee is best-effort

Unchanged: `processor.rs` performs the charge as `let _ = mgr.account_transfer(…)`, so a refused
charge does not fail the registration. The card describes it as best-effort. Whether the program
should fail the charge is an owner/contract decision (`docs/DEFECT_LOG.md` §13.3).

### R-3 (P3, from v30) The batch registration queue is unreachable

Unchanged and still the owner's in-flight feature (`docs/DEFECT_LOG.md` §13.4). It renders no review
when reached and calls `submitReviewedReview` in a loop.

## Method notes

- The probe (`/tmp/probe-record.mjs`, not committed) stubs `chrome.storage` and the SDK client
  boundary, then drives `domainRecordFacts`, `domainRecordRecheck` and the decoder with the real
  modules. It reproduced E-1, E-3 and E-4 before any fix, and its cases were then moved into
  `test/test-name-records.mjs` so the evidence survives this document.
- The test suite cannot catch a wrong-but-plausible chain read: `TCR_ABSENT`-style pins are tested
  against fixtures. What it can catch — and now does — is a call that never reaches the chain, a
  decoder that mislabels a state it was handed, and a signing path that bypasses auth.
- Live-network claims are unchanged by this pass. Nothing here was verified against Betanet; the
  two new name paths remain `IMPLEMENTED + TESTED (deterministic)` and `UNVERIFIED` on the live
  chain, exactly as the v31 merge left them.
